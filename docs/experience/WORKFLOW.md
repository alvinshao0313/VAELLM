# 实验记录与经验更新流程

本流程用于实验记录和经验更新；既有正文的归组、归档及引用保留遵守[文档管理规范](../MANAGEMENT.md#怎样整理既有长文)。入口：[经验库](README.md)。

## 分类与命名

| 内容 | 保存位置 | 组织方式 |
| --- | --- | --- |
| 实验结果总结 | `records/<研究主题>/YYYY-MM-DD_<简短实验名>.md` | 按研究主题、再按日期；同一受控 A/B 组共用一份总结，列出各 run_id |
| 踩坑与方法经验 | `lessons/<一级分类>/<二级专题>.md` | 三级为具体经验小节；先定位阶段或通用领域，再更新已有问题条目 |
| 历史方案/审查 | `history/` | 保留历史依据，不当成当前结论 |
| 原始证据 | 既有实验输出目录 | 配置、指标、核心日志、复现入口；文档只链接 |

分类及专题唯一导航见[经验库分类表](README.md#按问题查找)，可用 `python tools/docs.py categories` 查询检索名称。原 `liftquant_recovery`、`residual_lora`、`output_losses`、`checkpoint_lifecycle` 等旧专题入口保留锚点及去向，不再追加新正文。现有 `records/experiments/`、`records/docs/` 等迁移结构保留；同主题已有路径时沿用它，不另建平行目录。不按“成功/失败”分类，因为一次失败可以带来有效经验，一次成功也可能不具备可推广性。

用已有 run_id 或输出目录标识实验，不再维护一套重复编号。跨主题通过标签和链接关联，不复制正文。摘要不重复保存完整参数、全量指标或日志；实际 argv、配置、进程身份、退出与分数优先引用既有 JSON／日志，人工维护假设、可比较性、解释和决定。

## 实验前

1. 先按阶段或通用领域选分类，再用 `search '关键词' --category <分类> [--topic <专题>]` 定位经验；必要时扩大到相关分类及 `--scope lessons`。搜索主题词、模块、目标和报错，阅读相关条目及原始证据。
2. 在本次结果文档先写最小设计：假设、指定基线、改动变量、固定条件、主指标、成功/停止标准、资源预算和参考经验；明确回答配方选择还是机制归因，写清存储／曝光／更新预算口径。本组闭合前不更换共同父源或恢复配方。
3. 核对模型与数据版本、压缩/训练范围、实际学习率序列、评测口径和资源授权。重新尝试失败路线要说明改变了什么。

一次实验从计划到结束持续更新同一份结果总结，无需额外创建“计划版/进度版/最终版”。

## 实验结束

成功、失败、中止和方案被替代都走相同收尾：

1. **确认事实。** 核对退出状态、实际执行配置和原始指标；区分“程序完成”与“方法有收益”。后台仍运行时只更新启动状态，不持续轮询，不提前写最终结论。
2. **更新结果总结。** 写出相对指定基线的结果、可比较性、失败/异常、仍未证实的部分，以及继续、修改或停止的决定与理由。
3. **判断经验增量。** 有新认识则定位一级分类、二级专题和三级问题条目，并建立结果→经验、经验→结果的双向链接；跨分类只引用一份正文。同条件重现补来源，条件变化补适用分支，结论变化修订原规则；没有新认识就写“无新增经验”及原因，不另追加一段日期流水。写前重读，合并并行任务的新总结；旧入口的补写须保留后归入适用专题。
4. **处理冲突。** 新证据与旧经验矛盾时保留双方条件，说明是实现已修复、实验条件变化还是尚未解释。标注旧结论的适用范围或替代关系，不静默覆盖，不把历史失败变成永久禁止。
5. **更新计划与导航。** 当前计划原位更新在途任务、预算和下一决策，结束批次与旧交接回到所属记录。新主题才加入 README；具体实验由 `python tools/docs.py index` 登记，CATALOG 保留首次迁移快照。入口不追加进度流水或复制主题文档的数字。
6. **清理产物。** 确认证据和复现信息已保留，再按项目既有授权清理无用途权重和临时文件。保留的 checkpoint 写明具体用途；不因生成经验文档就删除必要证据。
7. **汇报与讨论。** 向用户汇报结果、对照差异、成本、限制、经验与清理情况；下一批方案按[项目规范的阶段推进条款](../../AGENTS.md#需求判断与协作)与用户讨论，不能仅更新文档后直接视为已讨论。已确认的批内后继照原条件执行。

## 分开记录两类状态

- **运行状态：** 计划中 / 运行中 / 已完成 / 失败 / 中止。程序 PASS 只表示对应检查完成。
- **结论：** 支持本次假设 / 本配置无收益 / 证据不足 / 对照不可比。不要强行将每次实验归为有效或无效。
- **经验的证据状态：** 待验证解释 / 本配置实测支持 / 已在注明条件下重复验证 / 已被修正或替代。只有真的追加了相应证据才升级状态。

经验条目注明模型/版本、方法、数据与预算等关键适用条件及最后核查日期。单次运行的泛化性有限；失败原因未证实时明确写“假设”。重试前检查旧问题是否已由代码或条件变化消除。

## 结果总结最小内容

以下内容放在同一份 Markdown 中，按任务规模缩短：

- **身份与状态：** 日期、主题/标签、run_id、运行状态、结论状态。
- **问题与设计：** 假设、指定基线、唯一变量或已知混杂、参考经验及规避动作。
- **实际条件：** 代码版本/差异、初始模型、数据、训练与评测口径；链接实际配置和复现入口。
- **结果与限制：** 少量核心指标及基线差值、异常、证据不足之处；链接原始指标与核心日志。
- **决定与经验：** 下一步或停止理由、对应经验链接；没有新增经验时如实说明。
- **保留与清理：** 必要证据位置、模型保留用途或已清理说明。

结果文档写“发生了什么、证据是什么”，不把尚未验证的原因写成事实。

## 经验条目最小内容

优先更新已有主题小节，按触发条件命名；篇首用简短表格链接这些小节。每行说明“遇到什么 → 先做什么 → 支持范围／证据状态”，不要把全部指标复制进表格。小节按以下顺序组织，已有证据可用普通段落表达，无须每次填写一套表单：

- **问题/触发条件：** 何种情况下会遇到。
- **归属与条件：** 从分类和专题进入；正文写明阶段、实际更新对象、模型／方法及关键预算。逐类恢复与压缩后恢复分开，跨阶段引用须保留证据边界；不额外维护重复标签台账。
- **建议动作：** 优先检查或调整什么，什么观察会改变下一步；先给动作再展开证据。
- **证据状态与来源：** 日期、对应结果链接；区分实测和解释。
- **原因/机制：** 已证实什么、仍假设什么。
- **适用边界：** 哪些条件可用、哪些尚不能推广。
- **迁移规则（涉及模型适配时）：** 区分固定方法、需按模型重算的配置和有限调节超参；写清哪些条件会改变结论、如何测量、相应默认／调整范围及停止规则。缺证标待定，单模型最优不写通用规律，跨模型只声明实际覆盖范围。
- **修订：** 新证据、被替代结论及替代链接，必要时保留简短变更说明。

相同规则的新实测归并到该小节，保留条件差异、反例和修订关系；日期用于标明证据时间。已有长串日期条目按完整问题归组，旧标题和原始来源保留可追溯入口。无需每次重写整篇或增加新文件。

故障修复若适合自动验证，应优先复用/补充有意义的回归检查，避免经验只停留在文字上。文档整理只验证信息保留、索引、相关链接和锚点；全库既有缺链单独说明，不触发额外训练或全量测试。
